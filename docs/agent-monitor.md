# Agent Monitor

!!! NOTE

    This is an enterprise-level feature of Security Onion. Contact Security Onion Solutions, LLC via our website at <https://securityonion.com/pro> for more information about purchasing a [Security Onion Pro](security-onion-pro.md) license to enable this feature.

Agent Monitor provides real-time visibility into autonomous background AI agents and scheduled automations (such as Alert Triage) executing across the grid.

This screen is located under the **Administration** menu on the left side of the Security Onion Console and requires the `automations/read` permission, which is granted to the `analyst`, `auditor`, and `superuser` roles. It is also accessible directly from the **Automated Agents** section in [Onion AI](onion-ai.md).

## Controls and Scheduler Status

The top toolbar offers quick controls for supervising active execution:

- **Breadcrumbs**: Navigate between the main overview and detailed execution transcripts.
- **Pause / Resume**: Freezes live updates so analysts can inspect in-flight work without the view changing, or resumes live polling.
- **Refresh**: Manually reloads current execution state.
- **Documentation Link**: Quick access to Onion AI documentation.

If the background scheduler is stopped or paused, an alert banner appears at the top of the page.

## Agent Pool Metrics

Summary stat pills at the top of the screen give an immediate health check of agent pool capacity:

- **Pool Running**: Displays the count of currently running tasks compared against the maximum concurrency limit (e.g., `2 / 5`). The value turns yellow to warn operators if the execution pool reaches saturation.
- **Pool Queued**: Displays the count of tasks currently waiting in the execution queue compared against the maximum queue depth (e.g., `1 / 20`).
- **Peak Running**: The all-time peak number of concurrent tasks executed by the pool.
- **Peak Queued**: The highest queue depth observed.
- **Rejected**: Count of task submissions refused by the pool because the queue was full. Displays in red if any submissions have been rejected.

### Understanding Rejected Items

The execution pool protects the grid from resource exhaustion by enforcing a maximum queue limit (`MaxQueueDepth`). When the queue is full, new task submissions are rejected. Here is what happens to those rejected items:

- **Automatic Requeueing for Automations**: Work items generated by scheduled automations (such as Alert Triage) are **not lost or deleted** when rejected. The automation engine catches the queue-full condition and automatically returns the work item to the `pending` backlog. The scheduler will re-attempt the item on a subsequent cycle once queue space or running slots become available.
- **Checkpoint Preservation in Applying State**: If an item was rejected while in the `applying` state (meaning the LLM has already finished its analysis and the agent was attempting to commit changes such as acknowledging alerts or adding tags), its completed results are safely preserved. When retried, the agent resumes directly at the application step without re-running model queries.
- **Retry Limits**: Work items track their attempts and failures. If an item repeatedly fails or cannot be processed across multiple automation runs, it eventually transitions to the `failed` state after exceeding maximum failure limits, preventing broken items from looping indefinitely.
- **Operator Guidance**: A non-zero or rising **Rejected** counter indicates that background workloads are outpacing worker throughput. Administrators should:
    - Review the schedule interval of active automations in [Agent Studio](agent-studio.md) (e.g., lengthening intervals or tuning alert query filters to reduce batch sizes).
    - Review **Max Concurrent Instances** on active agents to allow sufficient concurrency.
    - Check for slow upstream LLM provider responses that may be causing running tasks to hold slots longer than usual.

## Work Item Lifecycle

Automated tasks move through defined execution states:

- **Pending**: The work item has been discovered and queued, awaiting an available worker instance.
- **Running**: An agent has claimed the item and is actively analyzing data, executing model turns, or invoking tools.
- **Applying**: The agent has concluded its investigation and is committing changes (such as tagging alerts, acknowledging events, or creating cases).
- **Succeeded**: The work item finished its run successfully.
- **Failed**: The task encountered an unrecoverable error or exceeded its retry attempts.
- **Skipped**: The work item was bypassed (for example, if the target alert was already resolved).

## In-Flight Work Items

The **In-Flight** panel lists tasks that are currently queued, executing, or applying updates across the grid.

### Table Columns

- **Automation Name**: The name of the automation driving the task. Users with administrative privileges can click the name to jump straight to its editor in [Agent Studio](agent-studio.md).
- **Group**: The identifier of the workload group (such as a specific alert ID or investigation cluster).
- **Status**: Visual chip indicating whether the item is `pending`, `running`, or `applying`.
- **Doing**: Live phase indicator revealing what the agent is currently doing in real time, such as waiting for a model completion or invoking a specific tool (e.g., `invoking_tool:query_events`).
- **Agent**: The active agent and delegation chain responsible for the item (e.g., `Hunter` or `Hunter -> Case Analyst`).
- **Attempt**: Current attempt number out of total allowed retries.
- **In State**: How long the item has remained in its current state.
- **Elapsed**: Total time elapsed since the work item was initially created.
- **Actions**: Click the **binoculars icon** to open the live execution transcript.

### Expanded Work Item Inspector

Expanding an in-flight row opens an inspector card with four subtabs:

- **Details Subtab**: A key-value summary of the item ID, parent Automation ID (with a direct link to Agent Studio), Automation Kind, Group Key, State, Created timestamp, and Updated timestamp.
- **Payload Subtab**: Displays the exact input parameters and raw data supplied to the automation for this work item.
- **Attempts Subtab**: Lists every attempt made on this work item, showing the attempt number, session UUID, live status chip, start time, and a binoculars icon to inspect that specific attempt's transcript. Alerts if any attempt was orphaned due to unexpected worker restarts.
- **Result Subtab**: Displays intermediate conclusions, actions taken, or error causes.

## Recent Work Items

The **Recent** panel displays completed, failed, or skipped tasks from previous automation runs across the grid.

### Table Columns

- **Automation Name**: Name of the completed automation.
- **Group**: Workload grouping identifier (e.g., target alert ID).
- **Status**: Visual chip showing the terminal outcome:
    - `succeeded`: Task finished successfully and conclusions were recorded.
    - `failed`: Task failed after exhausting available retries.
    - `skipped`: Task was intentionally bypassed.
- **Agent**: Agents and sub-agents that participated in the workflow execution.
- **Attempt**: Number of attempts required.
- **Duration**: Total execution duration.
- **Finished**: Timestamp when the task completed.
- **Actions**: Click the **binoculars icon** to review the completed transcript.

### Inspecting Completed Work Items

Expanding a recent row opens the inspector card:

- **Details**: Full lifecycle timestamps and runtime metadata.
- **Payload**: The original event or alert payload that triggered the run.
- **Attempts**: Complete audit history of every session attempt, with start timestamps and links to each attempt's transcript.
- **Result**: Summary conclusions generated by the agent, actions taken (such as tags applied or cases created), or error diagnostics explaining why a run failed.

## Live Transcript View

Selecting the binoculars icon on any in-flight or recent item opens the live, step-by-step transcript view.

### Transcript Controls and Status

- **Agent Title & Model**: Displays the active agent name and the underlying LLM executing the run.
- **Live Badge**: A pulsing chip appears when the task is actively executing, indicating real-time streaming updates.
- **Auto-Scroll**: Streams model turns and tool results as they happen without requiring manual page reloads.

### Inspecting Agent Reasoning and Tool Execution

- **Chain-of-Thought Reasoning**: Agent internal thoughts appear in an expandable accordion labeled with a lightbulb icon. Expanding this view reveals the agent's step-by-step hypothesis generation, query planning, and evidence evaluation.
- **Tool Use Cards**: Every tool execution is displayed in an interactive card:
    - **Tool Name & Parameters**: Formatted code block showing exact parameters passed to the tool (such as OQL queries, alert IDs, or detection filters).
    - **Status Indicator**: Visual indicator showing whether the tool is pending, actively executing, completed, or failed.
    - **Raw Results**: Expandable accordion displaying the structured data returned by the tool.
- **Nested Delegations**: When an agent delegates sub-tasks to subordinate agents, the delegation appears as a nested panel:
    - Displays the delegated sub-agent identity.
    - Tracks credits and tokens consumed by the sub-agent.
    - Contains the sub-agent's own thoughts and nested tool executions.
- **Open in Chat**: Analysts with appropriate chat permissions can click the **Open in Onion AI** button to load the session directly into the [Onion AI](onion-ai.md) chat window, allowing them to ask follow-up questions and continue the investigation interactively.
